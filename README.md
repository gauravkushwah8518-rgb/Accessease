# AccessEase

**AccessEase** is a universal web accessibility toolkit and embeddable widget. It lets any
website offer dyslexia-friendly reading, text-to-speech, voice navigation, color-blindness
previews and more — activated by visitors with a single floating panel, and installed by
developers with a single `<script>` tag.

Everything is written in plain HTML5, CSS3 and JavaScript. There is no framework, no build
pipeline to speak of, and **zero runtime dependencies**.

---

## Features

| # | Feature | What it does |
|---|---------|--------------|
| 1 | Dyslexia-friendly typography | Switches the page to the bundled **OpenDyslexic** font with adjusted letter/word spacing |
| 2 | Text-to-Speech | Reads the page aloud in sentence-sized chunks (browsers truncate long utterances), with a speed slider |
| 3 | Voice navigation | Web Speech recognition that survives the browser's auto-stops — say "dark mode", "bigger text", "read page", "open panel"… |
| 4 | Color-blindness previews | Protanopia, Deuteranopia, Tritanopia and Achromatopsia via SVG color-matrix filters |
| 5 | Reading ruler | A focus bar that follows the pointer *and* the keyboard-focused element; nudge with `Alt + ↑/↓` |
| 6 | High contrast & dark mode | WCAG-conscious color schemes, toggled per visitor |
| 7 | Persistent preferences | All settings are saved to `localStorage` and re-applied on every page load |
| 8 | Enlarged cursor | A high-visibility pointer replacement for low-vision users |
| 9 | Link & button highlighter | Outlines every interactive element on the page |
| 10 | Keyboard nav helper | Always-visible focus outlines |
| 11 | Smart TTS fallback | If the browser's speech engine is broken or has no voices, reading falls back to a gentle auto-scroll so users can still read along hands-free |

### The marketing site itself

The four pages (`index.html`, `demo.html`, `docs.html`, `about.html`) are a demo of the
product's own aesthetic: a glassmorphism navbar (`backdrop-filter: blur(18px) saturate(150%)`
with an animated underline sweep), drifting ambient color orbs, a film-grain overlay,
mouse-tracking spotlight glow on cards, staggered scroll reveals, and a typewriter terminal
animation in the hero. All effects respect `prefers-reduced-motion`.

## Architecture

```
index.html / demo.html / docs.html / about.html   Marketing site pages
css/                 Site styles (variables, base, layout, components, animations, panel)
js/
  core.js            Shared accessibility logic — the single source of truth
  panel.js           The accessibility panel UI on this site (imports core.js)
  main.js            Navbar scroll, mobile menu, scroll reveals, card spotlight, orbs
  typingEffect.js    Hero typewriter line
  terminalAnimation.js  Hero terminal log animation
src/widget.js        Embeddable widget shell (imports core.js)
widget-build/        Generated single-file bundle — do not edit by hand
scripts/             Build + syntax/asset check helpers
tests/               node:test suite (runs under jsdom)
fonts/               OpenDyslexic-Regular.woff2
assets/images/       Logo + favicon
```

**The key design decision:** the site panel and the embeddable widget are two thin shells
over one shared core (`js/core.js`). This guarantees the features cannot drift apart — a fix
to text-to-speech in the core automatically applies to both.

The widget must ship as a *single plain `<script>`* for third-party sites, so it is
generated by concatenation:

```bash
npm install
npm run build:widget   # rebuilds widget-build/accessease.js from js/core.js + src/widget.js
```

CI fails if the committed bundle is stale.

## Running locally

The site uses ES modules and relative asset paths, so opening `index.html` directly from
disk hits browser CORS restrictions. Use any static server:

```bash
npm install
npm start          # serves on http://localhost:3000
```

Any static server works too (`python3 -m http.server`, VS Code Live Server, …).

> **VS Code Live Server tip:** open the *project folder itself* in VS Code before clicking
> "Go Live". If your VS Code window is rooted at your home directory, Live Server serves
> whatever `index.html` it finds there — quite possibly a different project's.

## Embedding on any website

Build the bundle, upload it, and point a script tag at it:

```bash
npm run build:widget
```

```html
<script src="/accessease.js" async
        data-position="bottom-right"
        data-lang="en-US"></script>
```

### Configuration attributes

| Attribute | Type | Default | Description |
|-----------|------|---------|-------------|
| `data-position` | string | `bottom-right` | Floating button position: `bottom-right`, `bottom-left`, `top-right`, `top-left` |
| `data-accent` | hex | — | Override the accent color used by the button and active tool states, e.g. `#ff6b6b` |
| `data-lang` | string | page's `lang`, else `en-US` | Language for speech synthesis and recognition, e.g. `hi-IN` |
| `data-storage-key` | string | `accessease_settings_v2` | localStorage key for saved preferences — change it if another script on your site uses the default |

### JavaScript API

The bundle exposes a small `window.AccessEase` handle:

```js
AccessEase.open();      // open the accessibility panel
AccessEase.close();     // close it
AccessEase.settings();  // current settings object
AccessEase.config;      // resolved data-* attributes
AccessEase.defaults;    // default settings
```

### Fonts

Upload `fonts/OpenDyslexic-Regular.woff2` to a `fonts/` folder next to the bundle and the
dyslexia font loads locally. Without it, the widget falls back to a CDN copy of the same
file, so the feature still works.

**There is no public CDN build.** Self-host the bundle, or host it on your own CDN.

## Development

### Scripts

| Command | What it does |
|---------|--------------|
| `npm start` | Serve the site on port 3000 |
| `npm run build` / `npm run build:widget` | Regenerate `widget-build/accessease.js` |
| `npm run check` | Syntax-parse every JS file + verify all referenced assets exist (dependency-free) |
| `npm test` | Run the `node:test` suite (45 tests) under jsdom |

### Tests

The suite covers the shared core (chunking, TTS queueing, engine-failure reporting,
voice-command restarts), the site panel (settings persistence, focus trap, feature
toggles) and the widget bundle (integration, staleness check, graceful degradation when
speech APIs are missing).

```bash
npm test
```

### Checks performed by CI

1. Every JS file parses
2. Every asset referenced by HTML/CSS exists on disk (and fonts/images are real binaries,
   not placeholder text files)
3. The full test suite passes
4. The committed widget bundle is not stale (`npm run build:widget` produces no diff)

## Browser support notes

- Speech synthesis needs the Web Speech API. Some Linux/headless environments expose the
  API but have no voices installed — AccessEase detects the failure and falls back to
  auto-scroll reading instead of dying silently.
- Chrome loads voices asynchronously; the widget waits up to a second for the voice list
  before speaking.
- Voice recognition requires HTTPS or localhost.
- Everything else (dyslexia font, filters, ruler, dark mode…) is plain CSS/JS and works
  everywhere.

---

## Project layout philosophy

- **One core, two shells** — features live in `js/core.js`; `js/panel.js` and
  `src/widget.js` only render UI and wire events.
- **No framework, no runtime deps** — the only devDependencies are `jsdom` (for tests) and
  `serve` (for local preview). The shipped bundle is fully self-contained.
- **Accessible by default** — the toolkit's own UI is keyboard-navigable, screen-reader
  announced (`aria-live`), focus-trapped, and reduced-motion aware. An accessibility tool
  that isn't accessible would be embarrassing.
